Ticmint Internet Listener

An agent that watches the public internet for event organisers who are frustrated with their ticketing platform, works out who they are and why they're worth contacting, and writes them to a Google Sheet that refreshes itself every few hours.

Built for the Ticmint Growth Lead assignment (Part A, Track 1). The written parts are in docs/ and on the submission site.
Live sheet Ticmint Internet Listener - Leads (live): tabs Leads, Review, Hot queue, Run log, About. Leads and Run log pull the repo CSVs with IMPORTDATA (Google refreshes roughly hourly); the Review tab is human-only and never overwritten
Proof it runs on its own data/runs.csv (one row per run) and the listen workflow history
Schedule GitHub Actions cron 17 */6 * * * (every 6 hours), plus on every change to the agent's code
Custom MCP server listener_mcp/server.py: 14 tools, 1 resource, 1 prompt

What talks to what. The scheduled job doesn't call any API itself. agent/run.py launches the MCP server as a subprocess, lists its tools, and runs the cycle in agent/pipeline.py entirely through call_tool. The server owns all I/O and all judgment. Because of that, the same server plugged into Claude Desktop answers questions against the same data:

"Who complained about Eventbrite payouts in the UK this week, and what should I say to the top one?" → query_leads(pain="payouts", region="UK", days=7) → the rows, with openers.

Where the LLM sits. In one place: qualify_post, after the rules and only for posts the rules shortlisted (score ≥ 30, max 40 per run). It returns structured JSON (is this an organiser, which platform, which pain, buying intent, an evidence quote, a score, a reason, an opener). Then a grounding check runs: the quote must appear verbatim in the post and the named platform must appear in the text, or the LLM's answer is thrown away and the rules decide. Final score = 0.4 × rules + 0.6 × LLM. If the LLM says "not an organiser", the post is dropped.

What triggers a run. The cron schedule; a push that changes listener_mcp/, agent/ or config/; the "Run workflow" button; or run_listener from a chat client.

Why rules first. Rules are free, deterministic and unit-tested (tests/). They also keep LLM cost flat however noisy the sources get, and they keep producing rows when a free LLM tier runs out. In that case the bar rises from 30 to 45, because there's no second opinion.

Where it breaks

These are from running it, not from guessing. Every run's errors are in data/runs.csv.

  • Reddit blocks cloud IPs. From GitHub Actions, reddit.com/search.json returns 403 on every run, PullPush (the public Reddit archive) returns 403 on most calls, and the RSS feed returns 429. Reddit is where organisers complain most, so this is the biggest gap. The fix is OAuth credentials (a free "script" app, 100 requests/min). Reddit has tightened API approvals, so plan for a short wait, or run the job from a residential IP (a $5 VM won't do; a home machine or a proxy will).
  • Signal is sparse and the rules are blunt. Run 1 kept 31 rows that were all noise (HN essays, conference-design blogs matching "support"). Run 4 kept 9 "Warm" rows that were organisers happily advertising events on Eventbrite, while a genuine lead (account suspended five days before an event) scored only 55. Run 5 still kept long event digests that mention Eventbrite once and "recommend" somewhere unrelated, so sentiment is now judged only within ±250 characters of the platform mention. Each fix came with a fixture test. By run 7 the rules kept 2 of 162 posts, one of them the genuine Hot lead. They'll keep missing new phrasings, though. The LLM pass is what makes precision acceptable. Without a key, expect more false positives.
  • GitHub cron runs late. Runs 1–9 were started by code pushes. The first cron slot (12:17 UTC, 21 Oct) didn't fire on time; the first schedule run started at 17:12 UTC, about 5 hours late. GitHub treats cron as best effort, especially on new repos and at busy times. So a separate scheduled check runs 30 minutes after each slot (:47 past 0/6/12/18 UTC) and, if no run started, dispatches the workflow through the GitHub API. Those runs show trigger = workflow_dispatch in the run log, so they're never mistaken for cron.
  • Run accounting lied once. Run 8 (21 Oct, 09:18 UTC) logged status: ok although Reddit had returned 429 on most queries: Reddit answered its first query, so it counted as a working source. Any source error now makes a run partial; old rows are corrected on read and a test reproduces the case.
  • Hallucination risk. The LLM can invent a quote, a platform or a pain. The grounding check rejects any answer whose quote isn't verbatim in the post or whose platform isn't mentioned, and marks the row rules (LLM rejected: …). What it can't catch is a plausible but wrong judgment ("is an organiser" when the author is a ticket buyer writing in the first person). That's why a human reads the row before any outreach.
  • Auth expiry. Bluesky sessions are created per run, so there's nothing to expire. A Reddit OAuth token is refreshed per run. A rotated Google service-account key or an un-shared sheet makes sync_sheet return error: … in the run log. The CSVs still update and the Apps Script path keeps working. Free LLM tiers rate-limit (Gemini free: ~10 RPM). Each error is logged and the row falls back to rules.
  • Cost at scale. Today it's free: Actions minutes on a public repo, free APIs, ≤ 40 LLM calls per run × 4 runs/day ≈ 5k calls/month, inside free tiers. At 10× the queries on a paid model it's roughly 50k classifications × ~1.2k tokens ≈ 60M tokens/month ≈ $5–20/month on a Flash/Haiku-class model. Cost isn't the constraint; source access is.
  • Fragile by design. Mastodon full-text search isn't public, so it reads hashtag timelines only. HN Algolia's fuzzy matching returns off-topic comments, which the relevance gate drops. data/state.json lives in git, so two simultaneous runs could race (prevented with a concurrency group). Region detection is keyword-based ("London", "₹", "DTCM") and leaves most rows blank.
  • Compliance. It only reads public posts and suggests replies. It never sends. Before automating sends: GDPR/PECR in the UK (legitimate-interest assessment, opt-out in every message), and each platform's rules on unsolicited DMs.

Two calls, for the walkthrough

  • The one I'd defend: rules before LLM, with a grounding check after. It's cheaper, testable, keeps running when the free tier dies, and it caught its own mistakes in public (the commit history shows each fix with the run that exposed it). An "LLM reads everything" design would have hidden runs 1 and 4 behind fluent summaries.
  • The one I'm unsure about: listening to public social platforms at all for this ICP. Ticmint's primary buyers (UAE/India mid-market promoters, Part D) mostly complain in WhatsApp groups and to peers, not on Reddit. The richer signal is probably an event-listing monitor (organisers announcing events on Platinumlist/District/Eventbrite, with dates and prices), which is the first thing on the list below.

Part B: The tracks I didn't build

The brief says "pick one of the five tracks" and lists four. I built Track 1, so these are Tracks 2, 3 and 4. Cost assumptions: Ticmint's scale is ~4 markets, ~10 competitors, a growth team of 1–3, a few hundred leads and a few thousand ad-platform rows a month. LLM costs are at small/fast-model prices (Gemini Flash / Haiku class), checked against their published per-token rates in Oct 2026, and rounded up.

Track 2: Review-site sentiment agent

Signal and source - New 1–3★ reviews of Eventbrite, Ticket Tailor, Platinumlist, TicketSource, Skiddle and Humanitix on Trustpilot (public pages, organisers write there about payouts and account holds), Capterra/GetApp and G2 (reviewer role, company size and industry are shown). Polled daily. G2 and Capterra are behind Cloudflare, so in practice this needs a paid scraper actor (Apify) or manual CSV exports. Trustpilot's public business pages are fetchable.

What it decides, and on what logic - Is the reviewer an organiser (not a ticket buyer)? On Trustpilot most Eventbrite 1★ reviews are buyers. Role words, "my event", payout language, and G2's role/company fields decide it. - Which specific complaint (fees, payout hold, account suspension, support, refunds), extracted with a quote that must appear verbatim in the review, the same grounding check as Part A. - Enrichment confidence: G2 gives "Event Manager, 11–50 employees, Events Services" plus first name and last initial. Matching that to a company or LinkedIn profile is a guess, so the agent scores the match and drops anything below "two independent fields agree".

Action and approval - Drafts a message that answers that complaint (e.g. payout hold → "on Ticmint buyers pay into your own Stripe, so there's nothing to hold"), logs to Freshsales and the Sheet. A human approves every send. A cold message that quotes someone's review back to them is borderline creepy and close to review sites' terms, so the human checks tone and whether to reference the review at all.

Failure mode that worries me most - Wrong-person enrichment. "Sarah K., Event Manager" matched to the wrong Sarah, who gets a message about a complaint she never made. That's reputational damage for little upside. The guard is confidence thresholds, and not mentioning the review unless identity is certain.

Monthly cost: Apify actors for G2/Capterra ≈ $30–50; LLM classification of ~2,000 reviews + 200 drafts ≈ $3; Hunter/Apollo free tiers for emails; GitHub Actions free. ≈ $35–60/month.

Track 3: Multi-tool orchestration ("what did we spend last week and what did it produce?")

I've built a working version of this for a dental clinic client: the Elites marketing dashboard. It shows Google Ads, GA4, Search Console, Microsoft Clarity and website leads in one view, with Business Profile and Meta awaiting access. Each number keeps its own source, and it flags broken tracking with the evidence (e.g. GA4 receiving booking and call events with none marked as key events), which is Track 4's job too.

Signal and source - A plain-language question from the team (Slack or Claude), plus a scheduled Monday question. Sources: Google Ads API, Meta Marketing API, LinkedIn Marketing API (spend, clicks, conversions), GA4 Data API (sessions, sign-ups by source), Freshsales API (leads, SQLs, deals by source), GSC (organic). One custom MCP server per source, plus a metrics MCP server that holds the definitions.

What it decides, and on what logic - Query planning: which sources, which date range, which timezone and currency (UAE/India/UK accounts report in different ones). - Definitions, not improvisation: "produce" means Freshsales SQLs and first paid tickets, not platform-reported conversions. Those definitions live in a versioned semantic layer (YAML) that the LLM reads but can't change. - Join logic: UTM → GA4 source → Freshsales lead source, with a reported match rate, so you see how much spend is unattributable.

Action and approval - Read-only. It answers, shows the tool calls and the SQL behind every number, and flags gaps ("27% of SQLs have no source"). There's no approval step because it changes nothing. Pausing ads or moving budget is a different agent with different guardrails.

Failure mode that worries me most - A confidently wrong number that sounds right. The LLM adds Meta's "conversions" to Freshsales SQLs, or mixes AED and INR. The rule: the LLM never does arithmetic. Tools return computed totals, and the answer must cite the tool output for every figure. A nightly reconciliation test compares the agent's answers to fixed queries.

Monthly cost: all APIs free (Google Ads needs an approved developer token); BigQuery free tier for joins (GA4 export is free); LLM ≈ 300 questions × ~20k tokens ≈ $5–15; hosting on a $5 VM or Cloud Run free tier. ≈ $10–25/month.

Track 4: Funnel measurement agent

Signal and source - Synthetic journeys every hour: Playwright runs ticmint.com → pricing → "Start Creating Free" and "Book an Enterprise Demo" with a test UTM, and records which tags fire (GA4, Meta Pixel, LinkedIn Insight, GTM container IDs). The audit found two GTM containers, so the agent would have caught that on day one. - Volume monitors: GA4 Data API event counts by hour (sign_up, generate_lead, purchase), compared against the same hour-of-week baseline. - Downstream reconciliation: GA4 generate_lead vs Freshsales leads created vs Meta/Google reported conversions, daily. - Config diffs: GTM API container versions, so any publish is diffed and attributed.

What it decides, and on what logic - Broken vs quiet: a drop is "broken" if synthetic journeys fail or the ratio between stages (form submits ÷ leads created) breaks, and only "quiet" if all stages drop together (a low-traffic day). That ratio logic is what keeps alert fatigue down. - Severity = revenue weight of the step × hours broken. A dead demo form is P1, a missing scroll event is P4.

Action and approval - Slack alert with evidence (screenshot, network log, which tag, which GTM version changed and who published it), a GA4 annotation, and a ticket. No automatic fixes to GTM. A human publishes tag changes. The agent can also block a reporting run ("don't send the weekly report, lead counts are 40% under Freshsales") and that needs no approval, since it prevents bad data rather than creating it.

Failure mode that worries me most - Synthetic tests polluting the data they're protecting. Test sign-ups landing in GA4, Meta audiences and Freshsales. Guard: a dedicated test email domain and UTM, filtered at GA4 (internal traffic rule), the CRM (auto-delete) and Meta (exclusion). The second worry is alerting so often that people mute the channel.

Monthly cost: GitHub Actions or a $5 VM for Playwright hourly; APIs free; LLM only to write the alert summary ≈ $2. ≈ $5–15/month.

Part C: The Organic Visibility Agent

A design, not a build. Assumptions are written next to the decision they affect.

C1. Fundamentals

SEO, AEO and GEO, as I use the words

What the system does What "winning" means What it rewards
SEO (classic search) Ranks ten documents and the buyer picks one A click from a ranked position Relevance, links, technical health, intent match
AEO (answer engines: Google AI Overviews / AI Mode, featured snippets, voice) Answers the question on the results page, sometimes with a source link Being the cited source, or the brand named in the answer Short, extractable, well-structured answers; schema; being already trusted by the index
GEO (generative engines: ChatGPT, Perplexity, Gemini, Claude, Copilot) Writes a recommendation from what it retrieved plus what it learned in training Being named, named accurately, and named early, for prompts like "best white-label ticketing for a Dubai festival" Third-party consensus: review sites, listicles, Reddit/forum threads, comparison pages, consistent facts across the web

The practical difference: SEO is mostly won on your own site. GEO is mostly won off it. An LLM asked "what's the best Eventbrite alternative for a UK club night" repeats what G2, Capterra, Reddit and "best of" listicles say, and Ticmint is absent from most of those today (evidence below). AEO sits in between: the source has to rank first, then be easy to lift a clean answer from.

My hands-on work on this channel

  • Foremost Public Adjusters (South Florida, local services). Technical and on-page rebuild: crawl issues 19 → 0, 140 keywords mapped to pages, 24 pages rewritten. Found 0 of 247 live paid keywords were branded.
  • EveryWatch (global watch marketplace, Jan 2024 – May 2025). Reference-level content pages built for search, alongside a small paid budget.
  • Google Business Profile for Elites Dental Care and Gold Coins Club & Resort. Profile rebuilds for map-pack and local answer surfaces, the local version of AEO.

Outcome

  • Foremost PA: crawl issues 19 → 0 (site crawl). No ranking or traffic gain is claimed: the brand rebuild was specified, not confirmed live.
  • EveryWatch: monthly new users 9,113 → 182,782 (GA4, Jan 2024 – May 2025). That's all channels; I don't separate organic in this number.
  • Gold Coins: profile actions +11% while profile views fell 30% (Business Profile, Q2 → Q3 2026).

The lesson I'd bring to Ticmint: I've been strict about not crediting organic with results I can't isolate. That's why C4 is built around a holdout.

Audit: Ticmint's organic visibility (checked 20–21 Oct 2026)

The full audit behind this section is a 16-page PDF. It scores five areas (overall 4.8/10) and covers the site, SEO, social, paid, reviews, competitors and a 90-day plan.

Method: public checks only (sitemaps, robots.txt, llms.txt, page source, the "best of" pages that rank for money queries, G2/Capterra). No GSC, GA4 or Semrush access, so traffic numbers are deliberately absent.

What I found

  1. Ticmint is missing from the pages AI engines quote. For "best white label event ticketing platform 2026", the top results include TicketNews' 7 best white-label platforms (Nuweb, vivenu, Ticketor, Eventcube, Ticketsauce, SECUTIX, Ticket Tailor) and Zoho's best ticketing platforms. Ticmint appears in neither. These are exactly the documents a generative engine retrieves. This is the single biggest GEO gap, and no amount of on-site content closes it.
  2. Review footprint is near zero. Capterra 0 reviews, G2 7, against Ticket Tailor's 596 on Capterra. Answer engines lean heavily on review aggregators for "best X" prompts, so with no reviews Ticmint has no presence there either.
  3. The llms.txt advertises the wrong company. It exists (auto-generated by All in One SEO Pro), but it's a flat dump of blog posts: DTCM permit guides, NFT/blockchain ticketing, event news. It doesn't describe the product, pricing, proof or ICP. A file meant to steer LLMs is steering them to the 2023 story.
  4. Positioning drift is visible to machines. The site says "2% white-label ticketing", while YouTube, the 2023 launch press and ~10 NFT posts say "blockchain anti-scalping". Entity consistency is a GEO ranking input in all but name. Mixed signals produce hedged or wrong descriptions.
  5. Content built for volume, not buyers. 110+ posts, ~22 on DTCM with 3+ near-duplicates, year-stamped listicles ("in 2027") that read as templated AI, no named authors, and no comparison or alternative pages at all ("Eventbrite alternative", "Platinumlist alternative", "Ticmint vs Ticket Tailor").
  6. Index hygiene. 13+ draft/backup pages in the sitemap (/new-home-2/, /pricing-2025/, /terms-of-service-bak2/…), thin tag archives indexed, /case-study/ vs /case-studies/, robots.txt pointing at the non-www host, and a footer "Popular Searches" keyword block with a typo.
  7. AI crawlers are allowed. robots.txt has no rules for GPTBot, OAI-SearchBot, PerplexityBot, ClaudeBot or Google-Extended, so they all fall under User-agent: *. Good, and worth keeping deliberate rather than accidental.
  8. Strong raw material that isn't machine-readable. BAI +27% revenue, 23k+ India Open tickets, BFI 66.5k tickets, ISO 27001 / SOC 2, the DTCM authorisation. These are the facts an LLM should repeat about Ticmint, but they sit in images and card layouts, not in crawlable text with schema.

How it decides what to work on next

Every candidate (a query cluster, a page, or an off-site source) gets one number:

priority = value × gap × winnability × confidence  /  effort

value       = ICP weight of the cluster (Part D: UAE/India mid-market promoter = 1.0,
              federations = 0.8, UK self-serve = 0.3) × intent stage (BOFU 1.0, MOFU 0.5, TOFU 0.2)
gap         = best competitor's share-of-answer − ours, across classic rank, AIO citation
              and generative mention rate (0–1, the bigger the surface the bigger the weight)
winnability = can *we* move it? If engines cite our own pages for this cluster → high.
              If they cite G2, Reddit and third-party listicles → on-site content scores low
              and the *off-site* action (reviews, list inclusion) scores high instead.
confidence  = how stable the measurement is (panel variance, sample size); noisy gaps wait
effort      = hours, from a lookup table per action type

Two hard rules sit above the formula:

  1. Fix before you create. Any technical blocker on a money page (noindex, 404, canonical loop, broken schema) jumps the queue regardless of score.
  2. Off-site beats on-site when the citations say so. If 4 of the 5 URLs an engine cites for a cluster are review sites, the agent does not write a blog post. It proposes the review ask or the list pitch.

Worked example. "Eventbrite alternative UK": value 0.3 (UK self-serve) × 1.0 (BOFU) = 0.3; gap 0.9; winnability 0.4 (engines cite G2 and Reddit); effort 16h → 0.007. "Platinumlist alternative / Dubai festival ticketing": value 1.0, gap 0.8, winnability 0.7 (few third-party pages exist, so our own comparison page can become the source), effort 16h → 0.035. So the UAE page ships first, five times higher, even though the UK term has more search volume. That's the point: the logic is anchored to the ICP, not to volume.

What it produces

  • A weekly backlog (top 5 with the score breakdown and the reason), posted to Slack and a Sheet.
  • Content briefs: target cluster, the questions buyers ask (from GSC, panel prompts and listener posts), the competitors engines name, the facts from the fact store to cite, the schema to ship.
  • Drafts, saved to WordPress as drafts via the REST API.
  • Technical fixes from an allowlist (below), applied automatically and logged.
  • An off-site worklist: which list articles to pitch, which review sites to push, which Reddit threads deserve a genuine (human) reply.
  • A weekly visibility report (C4) and alerts when a metric moves outside its band.

Where the human sits, and why there

  • Approving the brief, not the draft. The expensive mistake is choosing the wrong page to build or the wrong claim to make, so the human signs off on what and why before any words exist. That's 10 minutes a week, and it's where judgment pays.
  • Before anything publishes that names a competitor, a price, a fee comparison or a client result. These are legal (comparative advertising in the UK, ASA/CAP code) and trust risks, and they're exactly the facts an LLM will later repeat about Ticmint.
  • All off-site outreach and community replies. An agent posting in Reddit threads is astroturfing, and it gets the brand banned from the forums engines trust most.
  • Not in the loop for crawling, scoring, measurement, schema/internal-link fixes on the allowlist, or alerting. Putting a person there adds delay and catches nothing.

What has to be true before I'd move the line (all of them, measured, for 90 days):

  1. A fact store exists and is enforced. Every number in a draft must resolve to a row in a versioned table (fees, plans, client results, certifications). A claim checker blocks drafts with unresolved numbers or competitor statements.
  2. Editors stop changing substance. Over ≥ 30 drafts, human edits are style only: < 5% of drafts have a factual or positioning correction.
  3. Published agent pages perform at least as well as human pages on indexation rate, CTR and panel citation, by cohort.
  4. Rate limit and canary. No more than 2 auto-published pages a week, first to a low-traffic section, with automatic rollback if indexation or rankings for that section drop.
  5. Rollback is tested. One click reverts any agent change, and someone has actually done it.

What's the damage if it goes wrong, and how fast would I know?

  • A domain-level demotion. Google's scaled-content-abuse and site-reputation policies act on the whole site, not one page. Ticmint is already showing early symptoms (year-stamped templated listicles, 22 DTCM variants). Detection: a manual action shows in GSC within days, but algorithmic demotion shows as a slide in non-brand impressions over 2–6 weeks. By the time it's obvious, recovery is months.
  • Wrong facts get learned. A draft that says "1% fee" or "Ticket Tailor charges 5%" gets crawled, cited and absorbed into model answers. Pulling the page doesn't pull the answer, so that damage lasts weeks to months. Detection: the prompt panel's accuracy check (C4) within a week, but correction is slow. This is the main reason the human gate is on facts.
  • Legal/commercial. An inaccurate comparative claim in the UK or UAE invites a complaint or a takedown, and enterprise buyers (federations, The Times Group) read the site. Detection: immediate if a competitor complains, invisible until then.

Collection

  • Prompt panel: ~120 prompts = 40 money prompts (BOFU, ICP-specific), 40 category prompts, 20 brand prompts ("what is Ticmint", "Ticmint vs Platinumlist"), 20 control prompts the agent never works on. 4 engines × 3 samples × weekly ≈ 1,440 calls/week. Responses are parsed by a small model into: brands named, order, URLs cited, Ticmint description, and an accuracy check against the fact store. 3 samples matter because outputs aren't deterministic. I report a share with a confidence interval, never a single run.
  • Rotation: 25% of non-control prompts are replaced monthly with real phrasings from GSC queries, sales-call notes and listener posts, so the panel tracks how buyers actually ask instead of becoming a test we teach to.
  • Model-release annotations: every engine/model update gets a marker on the charts, so a step change from GPT-x isn't credited to the agent.

How I prove the agent works (not just that numbers moved)

A holdout. Split the query clusters in the backlog into matched pairs (similar value and baseline visibility) and let the agent work on one side of each pair for a quarter. The effect is the difference-in-differences in share of answer and non-brand impressions, treated minus control. If the control side rises just as much, the market moved, not us. A second, cruder check is market-level: run the off-site push (reviews, list inclusion) in UAE first and compare to UK.

What number tells me to shut it down

  • Kill the whole thing if, after two quarters, the treated-minus-control lift in share of answer on money prompts is under 5 points and self-reported AI/organic attribution is under 5% of new demos. At that point it's costing more than paid search would, with nothing to show for it.
  • Kill autonomous actions immediately (keep measurement running) if non-brand organic clicks fall > 20% for 3 consecutive weeks without a matching market or model-release explanation, if GSC shows any manual action, or if the accuracy rate on brand prompts drops below 90%. Being described wrongly is worse than not being described.

F2. What I changed, in priority order

  1. Sheet that fills itself. A new sheet whose Leads and Run log tabs are IMPORTDATA formulas over the CSVs the agent commits. No keys, no script. A Review tab holds human decisions and is joined back by lead_id, so no refresh can overwrite them. Hot queue lists Hot and Warm rows. The old empty sheet is renamed "unused".
  2. Evidence-based scoring (scoring.py). Six criteria, each with the matched text as evidence: organiser 0–30, platform 0–15, problem 0–25, switching or near-term intent 0–20, identity 0–5, ICP 0–5. A post with no first-person organiser language is capped at 49 (below Warm). Hot (≥ 70) needs organiser and problem evidence. A competitor name alone is worth 15 at most. Ticket-buyer, promotion and noise penalties. Every row carries score_explanation, e.g. organiser 30 + platform 15 + problem 25 + intent 20 + icp 2 = 92.
  3. Per-lead fields. confidence, icp_fit, organisation_hint (marked unverified), event_context, evidence_quote (verbatim), score_explanation, next_action, review_status, plus the URL.
  4. Honest run accounting (pipeline.py). Each run logs discovered, new, shortlisted, qualified, Hot/Warm/Watch, LLM calls and errors, processing errors, per-source ok/failed/skipped and status (ok / partial / failed). A source with any error makes the run partial. A post whose processing crashes is not marked seen, so it is retried. Old rows are migrated on read.
  5. LLM safety. The LLM can only lower or confirm: if it says "not an organiser" the post is dropped; its quote must be verbatim in the post and its platform must be named, otherwise the verdict is ignored. Timeouts fall back to rules.
  6. CRM interface, clearly unconnected. export_to_crm maps leads to Freshsales fields and writes them to a local outbox, returning NOT CONNECTED. Nothing is sent anywhere.
  7. Dashboard. Pipeline and run panels now show discovered vs processed vs qualified, unique prospects, reviewed, scheduled vs push runs (from the GitHub Actions API, shown as "unavailable" if that call fails), failed runs, last successful run and per-source status.

F7. Feedback loop into scoring

  1. Every week a person reviews all Hot and Warm rows in the Review tab.
  2. Each rejection carries a reason (not an organiser, not ICP, other). The reason points at the criterion that was wrong.
  3. Monthly, compare criterion scores between Accepted and Rejected rows. A criterion that scores high on rejected rows gets narrower patterns or less weight; phrases from accepted rows that the rules missed become new patterns, each with a fixture test.
  4. Once there are ~200 reviewed rows, report precision per source and per tier, and move the Hot/Warm thresholds to where precision is acceptable.
  5. Downstream statuses (replied, demo, customer) show which signals actually predict revenue; those criteria get more weight.

Where AI did the work, where I overrode it, where it was confidently wrong

This whole submission was built with Claude Code: the code, the first drafts of every written part, and the GitHub/Drive plumbing. That's the job description, so I didn't avoid it. What matters is where it needed correcting. Every item below happened during this build and can be checked in the commit history or data/runs.csv.

Where AI did the work - Wrote the MCP server, the sources, the scoring rules, the tests and the workflows, and drafted Parts B–D from my audit notes and the two Ticmint research docs. - Ran the agent live on GitHub Actions within an hour of starting, which is why the first mistakes surfaced so fast.

Where it was confidently wrong 1. "Reddit's public JSON will work from GitHub Actions." It didn't: HTTP 403 on the first run. Its fallback, PullPush, was also confidently proposed and also returned 403 from Actions. Reddit now needs OAuth credentials or a residential IP. Both failures are in data/runs.csv, run 1 onwards. 2. "Organiser-phrased queries plus a pain lexicon will be precise enough." The first live run kept 31 rows and all 31 were noise: Hacker News essays on AI consciousness and #eventprofs blog posts that matched "support" and "slow". The fix was a hard relevance gate (nothing scores unless it names a platform or is about tickets) plus a stricter bar when no LLM verdict exists. Re-scoring run 1's 31 rows offline with the gate kept 0. Then run 4 showed the next blind spot: 9 "Warm" rows that were organisers happily advertising events on Eventbrite, while a real lead (account suspended five days before an event) scored only 55. Pain words now count only alongside a problem, anger or switching signal. Both posts became test fixtures. 3. SDK drift. It wrote against the MCP Python SDK 1.x API (FastMCP) while the installed version was 2.3, where it's renamed. It pinned mcp<2 rather than learn the new API under deadline. A defensible call, but the code wasn't right first time. 4. A regex it was sure about. The organiser pattern missed "I'm organising a conference". The fixture test caught it, which is why the tests exist. 5. Platform permissions. It assumed the GitHub integration could create the repository. It couldn't (403), so I created it by hand. 6. Its own success metrics. It put "951 posts fetched" on the dashboard, a sum that counted the same posts up to seven times, and called the schedule "running" before cron had fired once. It also kept a Hacker News comment about a bomb threat as a lead because it contained "sell tickets", and logged run 8 as ok while Reddit was rate-limited. An audit on 21 Oct caught all four; the fixes and tests are in Part F. 7. "The Sheet refreshes itself." The linked sheet was empty: the Apps Script it relied on had never been run. Replaced with formula-based import.

  1. "Reddit: ok." Even after fix 6, the run log listed Reddit under sources_ok whenever it answered one query and failed the rest. The run status was right (partial), the column wasn't. Caught on 23 Oct while re-running before submission. A source now counts as ok only if every call worked, old rows are corrected on read, and a test covers it.

Where I overrode it - Kept the rules engine as a first-class scorer instead of "LLM classifies everything". Rules are free, deterministic and testable. The LLM only sees the shortlist and must quote the post, or its answer is discarded. - No number goes in without a source. Part E uses only figures already published in my casebook, and says where a result isn't only mine (MR Jewels lifetime ROAS) or the data is flawed (double-counted purchases). - Picked UAE/India promoters as the primary ICP, though the listener finds its best leads in the UK/US Eventbrite segment. Volume of complaints isn't the same as commercial fit.

The pattern: AI was reliably good at producing working structure fast, and reliably overconfident about the outside world (what an API allows from a given IP, what real posts look like). The defence was to run it against the real internet early and write down what broke.
